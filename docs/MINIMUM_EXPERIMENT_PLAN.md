# 2026-08-20前最低补强实验方案

更新日期：2026-08-06

## 1. 目标和边界

目标不是在两周内把项目包装成“必然能中C会”，而是把它推进到：

- 开题报告有完整问题、方法、证据和后续路线；
- 论文主张与实际证据一致；
- 最致命的语义、外部有效性和基线缺口得到最小但可信的回答；
- 所有新增数据能重复生成并进入统一白名单。

本阶段冻结V1，不开发V2，不修改已有正式原始日志，不根据实验结果选择性删除合同。

## 2. 优先级

### P0：必须完成

#### E1. Harness语义适用性研究

研究问题：在什么条件下，生成Harness与Original Echidna测试的是可比较的属性行为？

任务：

1. 实现只读静态适用性检查器，至少识别：构造参数、payable、`msg.sender`、`tx.origin`、`msg.value`、区块变量、外部调用、delegatecall、自毁、多合同依赖、按调用者索引的映射；
2. 为现有11个正式合同生成逐项特征表和supported/conditional/unsupported结论；
3. 对已知触发序列做差分重放，比较Original多交易执行和Harness单交易执行后的属性相关状态；
4. 加入至少一个会因调用者或交易边界而产生差异的负面案例；
5. 把不支持范围写进生成器拒绝规则或明确警告，避免静默地产生不可比较结果。

主要指标：适用性类别数量、差分一致/不一致数量、拒绝/警告准确性、人工复核记录。

完成标准：不能只产出文字说明；必须有机器可读表、测试和至少一个实证语义差异案例。

#### E2. 公开属性基准扩充

研究问题：V1在预先声明、非按结果筛选的公开属性任务上是否仍能保留有效触发序列？

项目目标：从当前5个扩展到**至少12个、争取20个**合格公开任务。该数字是时间约束下的项目门槛，不是会议规则。

候选入口：

- Echidna官方测试和Building Secure Contracts练习；
- SmartBugs Curated中可表达为状态属性且需要多交易的合同；
- Trail of Bits可复用属性或公开Echidna项目；
- 其他具有明确来源、漏洞说明和可重放触发序列的开源合同。

预先声明的纳入条件：

- 来源、许可证和版本可固定；
- Solidity可在冻结环境中编译，或适配修改可机械记录；
- 存在原作者属性，或能依据公开漏洞说明按统一规则编写属性；
- 反例需要至少两步状态操作，单函数立即失败不能作为核心序列任务；
- 符合E1定义的支持范围，或单独列为unsupported而不进入性能比较。

排除规则：编译失败、依赖无法恢复、无法定义可信属性、只依赖当前Harness不支持的语义、无可验证反例。所有排除项都保留在筛选流程表，不得无痕删除。

防止选择偏差：

1. 只允许用编译、静态分析和已知反例做纳入筛选；
2. 在正式运行前冻结合同列表、属性、适配补丁、K和预算；
3. 不得因为V1失败而排除合同；
4. 原始分析失败、Harness生成失败和启动失败均进入分母或单独的端到端成功率。

正式设计：每个benchmark/method使用相同seed 1–30；保留Original、Full-K1和Full-K5；若成本过高，先做不用于主结果的编译/10-seed可行性批次，冻结后再运行30 seed正式批次。

#### E3. 公平基线

研究问题：收益来自属性定向序列选择，还是仅仅来自把任意序列封装进Harness？

最低内部基线：

- Original Echidna；
- Dependency或Property-only的matched-K版本；
- Full-K1与Full-K5；
- 一个等候选规模的随机排序/随机Top-K基线。

随机基线必须把“路径选择随机性”和“Echidna fuzz seed”分开记录。不能复用现有混杂的早期random pilot作为主基线。若运行预算有限，可使用预先冻结的多组ranking seed，并采用分层或混合效应分析，不能只抽一份幸运随机排序。

外部基线首选SMARTIAN，因为它与静态数据流交易序列生成最接近。先做可行性审计：

- 是否能获得并固定版本；
- 是否支持合同的Solidity/EVM版本；
- 其漏洞预言机能否与用户属性形成共同任务；
- 预算、初始状态、调用者和成功定义能否对齐；
- 输出能否保存完整日志和重放反例。

如果不能公平对齐，不得把不同漏洞预言机的“发现数”直接比较。应保留失败原因，改为比较共同可测的序列触达能力，或明确论文只具有内部基线而缺少外部SOTA比较。

截至2026-08-06，SMARTIAN 已固定版本并完成 Release 构建、短时校准、两个 SmartBugs 整数属性的 `IntegerBug`/Echidna 独立重放对齐，以及按 0.4.25、30 秒、30 次重复冻结参数完成的 60 次外部基线批次。该批次作为 C-1 外部工具对照，不追溯性纳入 C2 分母。详见[C2基线可行性报告](../results/public-benchmarks/c2-screening/baseline-feasibility-report-v7.md)、[SMARTIAN校准记录](../results/public-benchmarks/c2-screening/SMARTIAN_CALIBRATION.md)、[预言机对齐记录](../results/public-benchmarks/c2-screening/SMARTIAN_ORACLE_ALIGNMENT.md)和[正式批次摘要](../results/public-benchmarks/c2-screening/smartian-formal-20260806/README.md)。

#### E4. 可扩展性与候选增长

研究问题：静态分析和候选枚举是否能处理比当前合成合约更大的真实合同？

至少记录：

- Solidity行数、公共/外部函数数、状态变量数；
- 读写依赖边数；
- 路径深度和每函数最大访问次数；
- 枚举前/各阶段retained path数；
- 峰值内存、分析时间、Harness生成与编译时间；
- 超时、内存失败、分析不支持和候选截断。

不要只报告成功合同的中位数。失败、超时和截断必须进入端到端成功率。

### P1：有余力再做

- 参数K的敏感性曲线，而不只比较K1和K5；
- 候选分值与真实触发概率/排名的相关性；
- 对属性编写人工成本和所需领域知识的测量；
- 语义保持更好的Harness设计，例如保留调用者/价值或分步交易边界；
- 第二个外部工具基线。

### 明确不做

- 为了增加数字而重复更多相同seed；
- 混入V2开发结果；
- 把已有早期pilot与正式批次合并；
- 只挑选V1成功的公开合同；
- 在语义问题未解决前声称端到端加速；
- 因安装困难而静默删除外部基线。

## 3. 预声明研究问题

- RQ1：属性过滤、值匹配和重复访问分别怎样改变候选集合与目标路径排名？
- RQ2：在公开、多交易、具有明确属性的任务上，V1相较Original和matched-K基线是否提高预算内反例发现率？
- RQ3：V1是否降低反例发现时间；右删失下效应方向和不确定性如何？
- RQ4：Harness在哪些Solidity/EVM语义特征下保持可比较行为，何时会失败？
- RQ5：预处理时间和候选数量如何随合同规模、路径深度和重复上限增长？
- RQ6：与最接近外部工具相比，V1在共同任务上提供了什么额外能力或工程取舍？

## 4. 数据和统计口径

### 主要结果

- 运行级反例发现率，95% Wilson区间；
- 同seed方法比较使用exact McNemar；
- 同一研究族内使用Holm校正；
- time-to-falsification使用Kaplan–Meier和双侧log-rank，同时报告中位数是否达到；
- 端到端分析成功率，包括静态分析、Harness生成、编译和启动失败。

### 次要结果

- 目标路径是否进入Top-K；
- 候选减少率与tie-aware rank；
- 预处理耗时、峰值内存和候选增长；
- 属性编写/适配工作量；
- 语义一致率和不支持特征分布。

### 禁止混用

- Original外层调用数与Harness目标函数调用数；
- 单个property outcome与MultiProperty运行级成功；
- `budget_exhausted`与property passed；
- 不同配置/批次的简单pooled显著性；
- 不同漏洞预言机的原始“漏洞数”。

## 6. Go/No-Go检查点

### G1：新颖性

能否用一句话说明V1与SMARTIAN/MuFuzz的不同，并指出对应实现和实验？不能则暂停大规模运行，先调整研究问题。

### G2：语义

能否自动识别不支持合同，并对纳入合同提供差分一致性证据？不能则实验只能称为Harness执行效果，不能与Original作算法优劣结论。

### G3：数据集

合同是否在运行前按统一规则冻结，所有排除和失败是否可见？不能则存在严重选择偏差。

### G4：基线

是否至少有Original、matched-K/随机Top-K，并完成一个外部工具可行性审计？不能则完整会议论文说服力不足。

### G5：规模

是否展示候选数量与分析成本随真实合同规模增长的趋势，并包含失败？不能则“轻量、可扩展”只能限于小合约。
