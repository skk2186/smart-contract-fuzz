# 智能合约状态依赖引导模糊测试阶段总结

## 一、当前研究工作的总体进展

本阶段围绕 Echidna 在**多交易状态依赖漏洞**上的测试效率问题，完成了从基础验证、组件迭代到合成基准正式实验的一整套流程。

研究的核心目标是：在不修改 Echidna 内部实现的前提下，利用 Slither 对智能合约进行静态分析，自动识别与安全属性相关的状态依赖关系，并生成能够被 Echidna 直接调用的交易序列 Harness，从而降低随机模糊测试在无关调用路径上的探索成本。

当前形成的 V1 方法主要包含四个组成部分：

1. 安全属性相关性分析；
2. 状态读写依赖路径生成；
3. 状态值写入与 `require` 条件匹配；
4. 有界重复函数访问与自动 Harness 生成。

在合成基准实验中，V1 已经证明了各组件的基本有效性。

### 1. V1 的主要实验结果

在 NoisyFourStep、ResetExample、BranchValue 和 RepeatedCall 四个主要合成基准上：

- V1 完整方法共运行 120 次，成功发现漏洞 120 次；
- 原始 Echidna 共成功 111 次，成功率为 92.5%；
- 属性相关性筛选将依赖候选路径总数从 92 条减少到 31 条，候选路径减少约 66.3%；
- 自动分析、路径生成和 Harness 编译的总准备时间约为 1.31 秒/合约；
- 四个基准中，V1 最终均能够将正确交易序列排在第 1 位。

进一步加入 AlternativePath 和 MultiProperty 后，六组主要合成实验中：

- V1 Full-K1 共成功 180/180 次；
- 原始 Echidna 共成功 171/180 次；
- V1 在多条可行路径和多个安全属性场景下仍能够正常工作。

这些结果说明，V1 已经完成了研究方法的**可行性验证和组件有效性验证**。

但是，上述结论主要来自人为构造的合成合约，只能证明方法在受控场景下有效，尚不能直接说明方法能够稳定处理真实或公开智能合约。因此，研究需要继续向 V2 迭代。

------

# 二、为什么需要从 V1 迭代到 V2

V2 的提出并不是因为 V1 完全无效，而是因为 V1 已经解决了“能否找到正确交易序列”的问题，接下来需要解决“能否在更复杂、真实的合约中稳定保留正确路径并控制候选空间”的问题。

## 1. V1 的实验对象以合成合约为主

V1 的主要基准均根据研究组件专门设计，例如：

- BranchValue 用于验证状态值匹配；
- RepeatedCall 用于验证重复函数调用；
- ResetExample 用于验证干扰路径；
- NoisyFourStep 用于验证属性相关性筛选。

这种实验设计适合做消融实验，但可能存在以下问题：

- 合约结构较简单；
- 漏洞路径在设计时已经明确；
- 状态变量、函数和安全属性之间的关系较直接；
- 缺少继承、内部调用、Getter、旧版 Solidity 等真实工程结构。

因此，V1 的高成功率不能直接等同于真实合约上的泛化能力。

V2 首先需要解决的就是**从合成有效性向公开基准有效性过渡**。

------

## 2. 有界重复访问会带来新的候选路径膨胀

V1 引入有界重复访问后，可以发现必须多次调用同一函数才能推进状态的漏洞。例如：

```text
deposit() -> deposit() -> unlock() -> withdraw()
```

在 RepeatedCall 中：

- 每个函数最多访问 1 次时，成功率为 0/30；
- 每个函数最多访问 2 次时，成功率为 30/30。

这说明重复访问机制是必要的。

但是，允许函数重复后，也会同时产生大量不必要路径，例如：

```text
begin() -> authorize() -> authorize() -> commit() -> execute()
```

在 ResetExample 中，属性相关性阶段能够将正确路径排在第 1 位；加入重复访问后，正确路径一度下降到第 5 位；随后依靠状态值匹配才重新回到第 1 位。

这说明 V1 的重复访问机制虽然提高了漏洞覆盖能力，却同时扩大了候选路径空间。随着真实合约函数数量增加，路径数量可能进一步增长。

因此，V2 需要增加更稳健的**候选路径约简机制**。

------

## 3. 简单的路径长度或分数比较无法判断路径是否冗余

在当前 V2 初版修改中，尝试使用路径支配关系删除冗余重复路径，但断言仍然失败。

根本原因是：两条路径即使长度相同、终点相同，也不一定具有相同语义。

例如：

```text
init() -> run()
run()  -> run()
```

这两条路径都是长度为 2 的序列，但其含义完全不同：

- `init() -> run()` 依靠初始化函数改变前置状态；
- `run() -> run()` 依靠同一函数的累积执行推进状态。

对于 SmartBugs 的重复调用漏洞，`run() -> run()` 可能正是触发漏洞所必需的路径，不能因为其中存在重复函数就直接删除。

这暴露了 V1 的一个重要不足：

> V1 对路径的评价主要依赖读写依赖、属性相关性和局部值约束，但缺少对整条路径状态效果的语义级比较。

V2 因此需要从“按结构删除路径”转向“按状态语义判断路径是否真正冗余”。

------

## 4. V1 的状态值匹配仍然是轻量级局部分析

V1 当前能够处理的主要模式包括：

```solidity
state = 2;
require(state == 2);
```

或者：

```solidity
state = 1;
require(state > 0);
```

其优势是分析开销低，不需要 SMT 求解器，也适合普通计算机运行。

但这种方法仍存在边界：

- 难以处理复杂算术表达式；
- 难以推导多次调用后的累积状态；
- 难以处理跨函数间接状态更新；
- 难以识别动态参数产生的精确值；
- `UNKNOWN` 路径较多时可能重新出现排序并列。

因此，V2 不一定需要直接引入重量级符号执行，但需要改进路径证据组合方式，使 `UNKNOWN` 不会简单地被当作无区别候选。

------

## 5. 真实合约中的属性相关性可能是间接的

合成基准中的安全属性通常直接读取状态变量，例如：

```solidity
function echidna_safe() public view returns (bool) {
    return state != 3;
}
```

但公开合约中可能通过 Getter 或内部函数间接读取状态：

```solidity
function echidna_not_paused() public view returns (bool) {
    return paused();
}
```

真正的状态变量可能在 `paused()` 内部读取，并且还可能来自父合约。

如果分析只查看安全属性函数自身的直接状态变量读集合，就可能无法找到真正相关的变量。

Slither 本身提供递归状态读取能力，例如 `all_state_variables_read` 可以包含内部调用所读取的状态变量。V2 需要在实现层面更系统地处理：

- 内部函数调用；
- Getter 函数；
- 继承状态变量；
- 父合约函数；
- 派生合约中的可访问函数。

------

## 6. V1 缺少公开基准兼容性验证

当前准备纳入的公开案例包括：

- Echidna 官方 `multi.sol`；
- Echidna 官方 `flags.sol`；
- Building Secure Contracts Exercise 2；
- SmartBugs MultiTx MultiFunc；
- SmartBugs MultiTx OneFunc。

这些合约包含不同类型的工程条件：

- Solidity 0.4.23 和 0.8.x；
- 继承关系；
- 间接属性读取；
- 多函数交易序列；
- 单函数重复调用；
- 重置和干扰函数；
- 参数约束和模运算。

因此，V2 的一个重要目标不是单纯提高合成实验成功率，而是建立一个能够适配公开合约的完整分析流程。

# 三、V2 相比 V1 的核心改进

V2 不应被描述为简单增加一个新的评分项，而应被定位为：

> 将 V1 从“能够生成正确路径的原型方法”，升级为“能够在公开合约上稳定生成、约简、解释和验证候选交易序列的方法”。

## 2. V2 改进一：语义感知的路径支配判断

V1 中候选路径主要按照综合分数排序，但无法主动删除明显冗余的重复路径。

V2 计划引入路径支配判断。一条路径只有在满足以下条件时，才能支配另一条路径：

1. 两条路径具有相同的目标安全属性；
2. 两条路径最终到达相同的目标函数；
3. 支配路径覆盖被支配路径所需的关键状态写入；
4. 支配路径的值匹配数量不少于被支配路径；
5. 支配路径的值冲突数量不多于被支配路径；
6. 支配路径不会删除触发漏洞所必需的重复调用；
7. 至少存在一项严格优势，例如更短、冲突更少或证据更强。

这种方式能够避免只根据以下因素错误删除路径：

- 路径长度；
- 是否包含重复函数；
- 原始属性相关性分数；
- 函数名称顺序。

当前断言错误说明支配规则与测试预期仍然没有完全一致，因此这部分暂时不能作为已经完成的实验结果，只能记录为 V2 正在解决的核心问题。

------

## 3. V2 改进二：保留必要重复，删除无效重复

V2 需要明确区分两类重复调用。

### 必要重复

重复调用确实推动状态逐步变化，例如：

```text
run() -> run()
deposit() -> deposit()
confirm() -> confirm()
```

若删除其中一次调用，漏洞将无法触发，这类路径必须保留。

### 冗余重复

函数再次执行后没有提供新的相关状态效果，或者只增加冲突，例如：

```text
prepare() -> authorize() -> authorize() -> execute()
```

第二次 `authorize()` 可能不会提供新的有效状态写入，反而造成状态冲突，这类路径可以降低排序或删除。

因此，V2 的重复路径处理原则应当是：

> 不因为函数重复而删除路径，而是根据重复调用是否产生新的安全属性相关状态效果决定是否保留。

------

## 4. V2 改进三：强化路径级证据组合

V1 的状态值分析主要对相邻函数之间的写入和条件进行匹配。

V2 将候选路径表示为多种证据的组合，包括：

```text
候选路径
+ 属性相关状态变量
+ 每个函数的读写集合
+ 常量写入
+ require 条件
+ 匹配数量
+ 冲突数量
+ 未知数量
+ 函数重复次数
+ 最终目标函数
+ 状态效果摘要
```

这样做的主要作用不是构建完整符号执行，而是使路径排序和约简具有更明确的依据。

------

## 5. V2 改进四：增强真实合约兼容性

V2 将增加对以下情况的处理：

- Solidity 0.4.x 和 0.8.x 编译器切换；
- 相对路径导入；
- 继承合约；
- 父合约中的状态变量；
- 派生合约中的安全属性；
- 内部函数和 Getter 间接读取；
- `int` 与 `int256` 等签名归一化；
- 同一函数在 Slither 与 Solidity 中的签名表示差异。

这部分属于工程兼容性改进，不改变论文核心算法，但直接决定方法能否在公开基准上运行。

------

## 6. V2 改进五：增加可解释输出

V2 不只输出最终 Top-K 路径，还需要记录每条路径为什么被保留、降权或删除，例如：

```text
保留原因：
- 写入目标属性相关变量
- 满足下游 require 条件
- 重复调用产生新的状态效果

降权原因：
- 存在值约束冲突
- 包含无贡献重复调用
- 目标函数前置条件不完整

删除原因：
- 被另一条状态效果等价但更短的路径支配
- 不再影响安全属性
- 无法到达目标函数
```

这能够为后续论文中的案例分析和错误分析提供直接材料。

------

# 四、当前 V2 的实际状态

当前 V2 已经进入候选路径支配与重复路径约简阶段，但尚未完成稳定验证。

目前遇到的断言错误表明：

- 当前路径支配条件可能仍然过强；
- 测试用例可能错误地假设所有重复路径都应删除；
- 必要重复路径与冗余重复路径尚未被完全区分；
- 路径状态效果的比较标准仍需统一。

因此，当前阶段应作如下处理：

1. 暂停继续增加新算法组件；
2. 保留 V1 现有稳定版本和实验结果；
3. 将当前修改单独作为 V2 开发分支；
4. 不用当前失败的断言结果支撑论文结论；
5. 先完成阶段总结和公开基准实验设计；
6. 后续再独立修复 V2 路径支配逻辑。

这种处理可以避免 V2 的未稳定修改破坏已经完成的 V1 合成实验结果。

## 第二阶段：完成公开基准 C-0 兼容性筛查

C-0 阶段只检查整个工具链是否能够运行，不进行大规模 30 次实验。

### 计划使用的公开合约

| 合约                                 | 主要测试内容               |
| ------------------------------------ | -------------------------- |
| Echidna `multi.sol`                  | 四步交易序列、重置函数     |
| Echidna `flags.sol`                  | 参数约束、状态依赖         |
| Building Secure Contracts Exercise 2 | 继承、Getter、间接属性读取 |
| SmartBugs MultiTx MultiFunc          | 多函数整数溢出路径         |
| SmartBugs MultiTx OneFunc            | 同一函数重复调用           |

### 每个合约需要依次检查

1. 原始合约能否使用对应 Solidity 版本编译；
2. Slither 能否正确提取目标合约；
3. 能否提取函数状态读写集合；
4. 能否识别安全属性相关变量；
5. `max_function_visits=1` 时生成哪些路径；
6. `max_function_visits=2` 时是否出现必要重复路径；
7. 值约束分析能否正常运行；
8. 正确路径是否进入候选列表；
9. 正确路径最终排名是多少；
10. 自动 Harness 能否成功生成和编译。

### C-0 中的失败分类

每个失败不能统一记为“方法无效”，而应分成：

- 编译器兼容失败；
- 导入路径失败；
- 继承解析失败；
- 属性相关性识别失败；
- 候选路径生成失败；
- 正确路径生成但排序靠后；
- Harness 生成失败；
- 方法本身无法处理。

这种分类能够区分工程问题和算法问题。

## 第三阶段：公开基准 C-1 正式实验

对于通过 C-0 的合约，再开展 30 个随机种子的正式实验。

### 建议比较方法

| 方法                 | 目的                         |
| -------------------- | ---------------------------- |
| Original Echidna     | 原始随机模糊测试基线         |
| V1 Full-K1           | 验证现有稳定方法             |
| V2 without dominance | 判断 V2 其他兼容改进的作用   |
| V2 Full-K1           | 验证语义路径约简后的完整效果 |
| V2 Full-K3           | 检查 Top-K 扩大后的稳定性    |

如果 V2 路径支配尚未修复，则先只运行 Original 和 V1，不应强行加入不稳定的 V2 数据。

### 主要评价指标

1. 漏洞发现成功率；
2. 成功样本的中位发现时间；
3. 超时未发现漏洞的样本数量；
4. 正确交易序列排名；
5. 候选路径总数；
6. 属性筛选后的路径数量；
7. 重复访问后新增路径数量；
8. 支配约简后剩余路径数量；
9. 静态分析和 Harness 生成开销；
10. Harness 编译时间。

需要继续注意：

> Original Echidna 的一次调用与 Harness 的一次调用语义不同，因此两者的 Total calls 不宜直接作为主要效率结论。

调用次数主要用于比较不同 Harness 方法，Original 与 Harness 之间应以成功率和发现时间为主。

# 六、统计分析方案

## 1. 成功率

对于每个方法和合约，报告：

- 成功次数；
- 总运行次数；
- 成功率；
- 95% Wilson 置信区间。

方法间成功率差异可以使用 Fisher 精确检验。

## 2. 时间到漏洞

由于部分运行会在预算结束时仍未发现漏洞，这些数据属于右删失数据，不应只比较成功样本的平均时间。

正式分析可采用：

- Kaplan–Meier 曲线；
- Log-rank 检验；
- 同时报告成功样本的中位发现时间作为辅助指标。

## 3. 候选路径数量

报告：

- 原始依赖路径数；
- 属性筛选后路径数；
- 重复访问后路径数；
- V2 约简后路径数；
- 路径减少比例。

## 4. 预处理开销

报告：

- Slither 分析时间；
- 路径生成时间；
- 值约束分析时间；
- Harness 生成时间；
- 编译时间；
- 总准备时间。

这样可以说明 V2 的静态分析开销是否能被后续模糊测试效率收益抵消。

# 八、阶段性结论

目前研究已经完成了从基础状态依赖分析到 V1 完整方法的迭代。V1 通过安全属性相关性、状态值约束匹配和有界重复访问，分别解决了无关路径过多、候选路径并列以及同一函数需重复调用的问题。合成基准实验表明，V1 能够稳定生成目标交易序列，并以较低预处理开销提高漏洞发现稳定性。

但是，V1 的实验结果主要来自合成合约。当方法被迁移到公开基准后，开始出现继承、间接属性读取、旧版 Solidity、同长度不同语义路径和重复路径膨胀等问题。尤其是必要重复路径和冗余重复路径不能仅依靠函数重复次数、路径长度或原始分数加以区分。

因此，V2 的核心不是继续无限增加分析组件，而是增强候选路径的语义表示、路径约简能力、真实合约兼容性和结果可解释性。当前 V2 的路径支配断言仍未稳定，应将其视为开发中的增强版本，而不是已经完成验证的正式方法。

下一阶段应首先冻结 V1，完成公开基准兼容性筛查和正式对比实验，再以回归测试为前提逐步完善 V2。这样既能够保住已经完成的实验成果，也能够使论文从“合成案例上的方法验证”进一步扩展为“公开基准上的有效性和泛化能力评估”。
