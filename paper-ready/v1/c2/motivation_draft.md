# 3 Motivation（中文草稿）

考虑一个属性要求最终状态 target == true。合约中有四类函数：某个初始化函数写入前置状态，某个目标函数在满足条件时设置 target，另有若干函数写入其他状态或把已经建立的状态重置。若只根据一般读写关系建立候选，初始化函数和目标函数可能被保留，但无关函数也可能进入候选池。随着函数数量增加，Echidna 需要在更多顺序和参数组合中寻找有效前缀；一个候选即使写入了相似类型的状态，也可能在中途把目标状态清掉。

NoisyFourStep 用一个受控的小例子隔离了这种干扰。其 Dependency 阶段可以产生 30 条候选路径，而属性相关过滤后只保留 3 条，目标路径成为唯一的 Top-1。这个现象说明，从 property 所读取的状态变量反向寻找相关写入，能够缩小“值得检查”的候选空间。它并不意味着减少候选数就必然减少端到端 fuzzing 时间，更不能把小型合成合约的结果外推到真实生态。

仅有属性相关性仍然不足以选择正确路径。设两个分支都写入属性读取的变量 flag，一个分支写入 flag = 1，另一个写入 flag = 0；后续属性需要前者。两条路径的状态依赖图完全相同，但值方向不同。BranchValue 的受控结果体现了这个障碍：只做 Property 排序时，目标路径可能不在 K1；引入简单写入值和 require 方向作为 value evidence 后，Value/Full 的 Top-1 可以对准目标。这里的值分析不是完整的符号执行，而是一个轻量、可解释的筛选证据。

另一个常见障碍是重复访问。假设第一次调用 deposit(x) 建立状态，第二次调用 deposit(y) 才能使累计值超过属性阈值。若序列生成器对每个函数只允许出现一次，图上的函数节点虽然存在，真正需要的路径却无法生成。RepeatedCall 以一个明确的重复调用目标展示了这一点：不允许重复的配置无法覆盖目标，而加入有界重复后，候选序列能够包含两次同一函数。bounded repeat 不是鼓励无限加长序列，而是在预先设定的访问上限内补充一种必要的状态到达方式。

重复扩展又会带来新的并列路径。例如，某个 reset 函数使多种排列具有相同的依赖分数，单纯依赖路径长度或读写数量时，正确路径可能在显示排名中靠后。ResetExample 说明，只有重复和依赖仍可能产生一个较大的同分集合；简单值条件可以进一步区分“建立状态后被正确使用”和“建立状态后又被清除”的路径。因此，Top-K 不是随意截断，而是要建立在能够解释的证据层次上。

这四个例子共同给出本文的设计动机：Property 负责把注意力集中到属性相关状态，Repeat 负责保留必须重复访问的路径，Value 负责提供值方向和条件匹配证据，Top-K 负责在有限 Harness 大小下保留可审计的候选集合。它们组合成 property-directed filtering + bounded repeat + value evidence + interpretable Top-K，而不是一个全新的模糊器核心。

上述例子都是 controlled benchmarks。它们通过有意构造无关路径、值方向冲突、重复调用和 reset 干扰来回答单个机制问题，不能代表真实合约中的调用者、资金、时间、外部调用或重入语义。对于真实或公开任务，还必须检查 Harness wrapper 与 Original multi-transaction model 是否在 caller、交易边界和回滚范围上可接受。正因为这些语义差异不能从静态读写图中自动消除，本文把 semantic boundary audit 作为方法评价的一部分，而不是把生成 Harness 当成天然等价的执行模型。
